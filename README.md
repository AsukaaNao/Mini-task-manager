# Mini Task Manager

A full-stack task management application built with **React, Tailwind CSS, Node.js, Express, and TypeScript**. It uses a JSON file (`backend/data.json`) for lightweight persistence and enforces a linear task-status workflow with chronological audit logging.

## 1. How to Run the Frontend and Backend

### Prerequisites

- Node.js 20 or newer
- npm 10 or newer

### Install dependencies

From the project root:

```bash
npm install
```

### Start the application

```bash
npm run dev
```

The app is expected to be available at `http://localhost:3000` when using the configured root orchestrator. The frontend and backend are run through the root development setup.

## 2. Brief Architecture Explanation

### Frontend

- React, TypeScript, Vite, and Tailwind CSS provide the user interface.
- UI components cover task lists, task details, task creation/editing, and workflow progression.
- An active-user selector simulates multi-user usage.
- The API client sends the selected user through the `X-User-Id` header.

### Backend

- Express and TypeScript expose the REST API.
- Request validation and task workflow rules are handled on the server.
- The current implementation keeps the backend logic in `backend/src/server.ts` to reduce structural complexity.

### Database

- `backend/data.json` stores users, tasks, and audit logs.
- Write operations are serialized, and updates are written to a temporary file before renaming it to reduce the risk of partial-file corruption.
- If persistence fails, the in-memory state is rolled back.

## 3. Assumptions Made

- **Status workflow:** Only one-step forward transitions are allowed: `to_do → pending → in_progress → done`. Skipped or backward transitions are rejected, and `done` is terminal.
- **Task ownership:** A task is associated with its creator when created; ordinary updates do not change that association.
- **Deletion:** Tasks and users are soft-deleted using a `deleted_at` timestamp so historical records can be retained.
- **Deployment:** The JSON file storage assumes a single server instance with a writable local filesystem.

## 4. Trade-offs Made

| Area | Chosen approach | Trade-off |
|---|---|---|
| Storage | JSON file | Simple to set up and inspect, but unsuitable for high write volume or multiple server instances. |
| Backend structure | One main `server.ts` file | Easy to navigate for a small task, but harder to maintain as features grow. |
| Write handling | In-memory state with serialized, atomic file writes | Reduces conflicting writes and partial-file corruption, but the full dataset must be managed in process memory. |
| Workflow | Strict linear status progression | Predictable and easy to validate, but does not support exceptions or custom workflows. |

## 6. Questions

### How do you ensure audit logs cannot be modified?

The API exposes audit history through a read-only endpoint. Audit entries are generated by the server when a valid status transition succeeds, rather than accepted directly from the client. 

This provides application-level protection against ordinary API updates, since there's no API that handles update or delete. But it still bhave a flaw since it is a `data.json` someone who had access to codebase can directly change the data

### Which part is most risky with many users?

The JSON persistence layer is the main risk. Each write requires serializing and saving the dataset, and a local file does not safely coordinate writes across multiple application instances. As data and concurrent traffic grow, this can cause latency, memory growth, and scaling problems.

### What would you refactor first if the system grew?

I would replace JSON file persistence with a relational database such as PostgreSQL first. This would provide transactions, constraints, and safer concurrent updates. I would then separate the current server file into routes/controllers, services for business rules, and a repository layer for data access, making each part easier to test and maintain.
